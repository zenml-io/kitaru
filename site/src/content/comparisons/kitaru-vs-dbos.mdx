Kitaru is narrower on purpose. It's built for Python agents, with `@flow`, `@checkpoint`, `wait()`, `kitaru.llm()`, and first-class replay in the box.

DBOS and Kitaru both solve the same first-order problem. When your agent crashes, you shouldn't start over. Where they differ is the shape of the code sitting on top, and the workload they were shaped for.

<FeatureWithGraphic title="Durable execution, shaped around dynamic agent loops">
  <DurableExecution slot="graphic" />

  DBOS and Kitaru both survive crashes. The real fight is over what kind of code sits on top.

  - **Code structure:** DBOS expects `@DBOS.workflow` bodies to be deterministic, with side effects pushed into `@DBOS.step`. Kitaru flows are plain Python functions. if/else, while, try/except, runtime-decided branches, all first-class.
  - **Checkpoint boundary:** In DBOS, every step is durable. In Kitaru, you mark with `@checkpoint` what's expensive enough that re-running it would burn real tokens. Everything a checkpoint returns is a versioned artifact.
  - **Replay:** `kitaru replay` resumes from the last completed `@checkpoint` and loads cached artifacts for everything upstream. You fix the bug at step 9, you don't re-pay for steps 1 through 8.
</FeatureWithGraphic>

<FeatureWithGraphic title="LLM calls as a first-class primitive" reverse={true}>
  <LLMPrimitive slot="graphic" />

  In DBOS, an LLM call is usually something you make inside your own step or through one of DBOS's AI integrations; it is not a DBOS-specific primitive in the way `kitaru.llm()` is. Kitaru treats it as the primary unit of cost, latency, and failure in an agent, and it shows in the API surface.

  - **API surface:** In DBOS you call `openai.chat.completions.create(...)` yourself inside a `@DBOS.step`. In Kitaru you call `kitaru.llm(prompt, model="fast")`.
  - **Key handling:** DBOS leaves it to you. Kitaru resolves the model alias and injects the provider key from the active stack.
  - **Cost and latency observability:** `kitaru.llm()` logs latency, token counts, and cost against the enclosing checkpoint. You don't need a separate LLM logging pipeline.
</FeatureWithGraphic>

<FeatureWithGraphic title="Artifact versioning across every checkpoint">
  <ArtifactVersioning slot="graphic" />

  In Kitaru, every checkpoint's inputs and outputs are persisted and versioned automatically, not just stashed for resumption.

  - **Cross-run lineage:** When using Kitaru, outputs from one run are artifacts you can reference, diff against, or feed into the next run. DBOS stores step I/O for resumption, not for comparison across executions.
  - **Diff in the same UI as the run:** With Kitaru, you can inspect execution artifacts, checkpoints, and logs through the UI or client APIs instead of digging through database tables.
  - **Cost attached to artifacts:** Each checkpoint in Kitaru carries the LLM calls beneath it and the dollars spent. Reasoning about what a run cost is part of the same view.
</FeatureWithGraphic>

<FeatureWithGraphic title="Framework agnostic, by design" reverse={true}>
  <FrameworkAgnostic slot="graphic" />

  Kitaru isn't trying to replace PydanticAI, OpenAI SDK, Claude Agent SDK, or raw Python. It sits underneath them.

  - **Adapter model:** Wrap your existing agent in a `@flow` and `@checkpoint` and you get durability without a rewrite.
  - **Inner loop vs outer loop:** Framework handles the inner loop (tool calling, context management, compaction). Kitaru handles the outer loop (durability, replay, artifact tracking, sandboxes, sessions).
  - **Not a framework or a tracing tool:** If you want a dashboard that logs spans, Kitaru isn't that. But if you want something that stops your 2-hour run from blowing up at the 97th minute, this is it.
</FeatureWithGraphic>

## Ready to try Kitaru?

If your durability problem spans Python, TypeScript, Go, and Java services, and your compliance story needs a SOC 2/HIPAA control plane today, DBOS is the tool for the job.

If your durability problem is shaped like a Python agent loop, Kitaru removes the glue layer you'd otherwise write on top.

`pip install kitaru`, add `@flow` and `@checkpoint`, and run your first durable agent in minutes. Check [the docs](/docs) for how `@flow`, `@checkpoint`, `kitaru.llm()`, `wait()`, and replay compose.
