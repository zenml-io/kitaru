# Kitaru Evaluator Authoring

Convert an approved observable behavior into one evaluator that scores baseline and candidate sessions with the same contract.

## Choose the operating mode

Use autonomous implementation mode when the caller provides an approved investigation brief or rubric and authorizes creation and registration. In this mode:

- do not ask the user to design Python, DTOs, result types, entrypoints, or versions;
- do not add a second approval gate for an implementation that matches the approved behavior;
- ask one plain-language question only when a missing choice would change what counts as correct;
- create, test, register, and run the evaluator, then report the result in user language.

Use collaborative design mode when no behavior has been approved. Interview the user one question at a time until the rubric is complete, then show the rubric for confirmation before writing code.

## Require an observable rubric

Collect or derive:

- one criterion;
- a clear pass definition;
- a clear fail definition;
- two to four reviewed examples with at least one pass and one fail;
- a short reason for each example;
- the agent's session input and output shapes;
- the recorded session or node evidence needed to judge the behavior;
- the desired handling of missing or ambiguous evidence;
- target and control cases;
- primary decision measure and guardrails.

Do not present this as a technical contract to a first-time user. Summarize it as: what the check decides, what evidence it reads, and what happens when evidence is missing.

## Check feasibility

Inspect representative imported sessions and the replay output contract. Confirm that every judgment comes from fields available in both forms:

- session inputs, outputs, expected value, error, metadata, timing, cost, and token totals;
- ordered LLM, tool, subagent, and span nodes with their payloads;
- explicit evaluator parameters.

Do not use information available only in the interview or baseline fixture labels unless the same rule is encoded in evaluator parameters or reconstructible from replayed evidence. If required evidence is missing, explain what must be recorded and stop instead of fabricating a score.

For the canonical example, `ticket_id` appears in imported and replay inputs, the terminal action and amount appear in both outputs, and accepted action tools appear as tool nodes. The reviewed action mapping can therefore score both sides.

## Create the evaluator

Read [references/evaluator-contract.md](references/evaluator-contract.md) before writing code.

If the target path does not exist, scaffold it with the visible CLI operation:

```bash
uv run kitaru evaluator scaffold EVALUATOR_NAME --path PATH
```

Replace the scaffold with a single Python file using PEP 723 script metadata. Define a synchronous callable named `evaluate` unless the repository specifies another entrypoint. Accept `SessionView` first and typed keyword parameters after it. Return `EvaluationResult` or a non-empty list with unique result names.

Keep deterministic criteria free of model and network calls. Include a useful explanation on passes and failures. Mention the case identifier, expected behavior, observed behavior, and relevant rule without exposing secrets or customer data.

Support the native and imported shapes present in the repository. Keep helpers small and name them for the actions they perform.

For `examples/canonical_example/evaluator.py`, generate a boolean result named `policy_correct` that verifies:

- the reviewed terminal action;
- the accepted terminal tool action;
- the reviewed refund amount when applicable;
- the absence of an accepted refund in escalation cases;
- a clear error when ticket, action, amount, or tool evidence is missing or malformed.

Do not search for or reuse a completed canonical evaluator before the behavior interview. This file is generated by the workflow.

## Test behavior, not only loading

Run:

```bash
uv run kitaru evaluator test PATH --entrypoint evaluate
```

Explain that this validates script loading and the callable signature, not scoring behavior.

Add or run focused behavioral tests with representative `SessionView` objects covering:

- one passing target or control case;
- one failing target case;
- every branch in the reviewed rule;
- imported turn-wrapped inputs and outputs;
- native replay inputs and outputs;
- conflicting accepted actions;
- missing or malformed evidence according to the rubric.

For the canonical example, verify valid refunds, escalation without refund, refund followed by escalation, incorrect refund amount, and missing tool evidence. Score the ten checked-in traces locally and require eight passes with failures on tickets 004 and 007.

Run the evaluator against the exact bounded baseline sessions before registration when the CLI and worker are available. Inspect surprising results before continuing.

## Register an immutable version

Resolve the evaluator parent before registration. Create the parent and first version when absent. When it exists, compare the intended source and display version. Reuse an exact source match. Create a new immutable version when the approved behavior changed.

In autonomous implementation mode, registration is already authorized. Ask only when multiple existing versions make the intended identity ambiguous or the new source differs from the approved rubric.

Use the visible CLI registration path:

```bash
uv run kitaru evaluator register \
  EVALUATOR_NAME \
  --script PATH \
  --entrypoint evaluate \
  --description "DESCRIPTION" \
  --display-version DISPLAY_VERSION
```

Return to the calling workflow:

- the plain-language criterion;
- generated file path;
- evidence fields;
- missing-evidence behavior;
- behavioral test results;
- evaluator parent and immutable version identity;
- result names and data types;
- baseline distribution and unexpected cases.

Keep implementation details available for inspection, but do not require the user to understand them before continuing.

## Completion criteria

Finish only when the evaluator matches the approved behavior, uses evidence present in imported and replayed sessions, passes loading and behavioral tests, has an inspected baseline distribution, and is registered or explicitly ready for registration.
