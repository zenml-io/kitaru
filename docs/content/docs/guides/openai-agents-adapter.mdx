title: OpenAI Agents Adapter
description: Make OpenAI Agents SDK runs durable, replayable, and streamable inside Kitaru flows
---

Kitaru's OpenAI Agents adapter is for the moment when you already have an
[OpenAI Agents SDK](https://openai.github.io/openai-agents-python/) agent and
want it to survive real workflow life: retries, replays, dashboard visibility,
and long-running execution traces.

Your agent stays an OpenAI agent. Kitaru adds the floor underneath it.

```python
from agents import Agent
from kitaru.adapters.openai_agents import KitaruRunner

agent = Agent(name="researcher", model="gpt-5-nano")
runner = KitaruRunner(agent, checkpoint_strategy="runner_call")
```

Once wrapped, you call the agent from inside a Kitaru `@flow`. Kitaru records the
agent run as one or more checkpoints, so a failed workflow can be inspected,
retried, or replayed instead of becoming a mystery pile of API calls.

## Install

Add the OpenAI Agents extra — and `local` if you want the local dashboard:

```bash
uv add "kitaru[openai-agents,local]"
```

Initialize the project once:

```bash
kitaru init
kitaru login        # local server; add a URL to connect to a deployed one
kitaru status
```

Set an OpenAI key wherever the flow code actually runs:

```bash
export OPENAI_API_KEY='sk-...'
```

<Callout type="warn">
  If your active Kitaru stack runs remotely, your laptop shell environment may
  not be visible to the remote runtime. Put `OPENAI_API_KEY` in the environment
  or secret mechanism used by that runtime before expecting remote executions to
  call OpenAI successfully.
</Callout>

## Quick start

This is the smallest useful shape: one OpenAI agent run inside one Kitaru flow.

```python
from agents import Agent
from kitaru import flow
from kitaru.adapters.openai_agents import KitaruRunner, OpenAIRunRequest

agent = Agent(
    name="researcher",
    instructions="Answer carefully and cite uncertainty.",
    model="gpt-5-nano",
)
runner = KitaruRunner(agent, checkpoint_strategy="runner_call")

@flow
def research(prompt: str) -> str:
    result = runner.run_sync(OpenAIRunRequest.start(prompt))
    return str(result.final_output)

handle = research.run("What should I know about agent durability?")
print(handle.wait())
```

Think of `KitaruRunner` as the adapter plug between two worlds:

- OpenAI still decides how the agent reasons, calls tools, and produces output.
- Kitaru decides where the workflow boundary is, how the call is checkpointed,
  and what can be replayed later.

## What Kitaru adds

For an existing OpenAI Agents SDK project, the adapter gives you:

- **Durable flow boundaries.** Agent work happens inside Kitaru executions that
  show up in the CLI and dashboard.
- **Replay and retry hooks.** Completed checkpoints can be reused when replaying
  a failed workflow.
- **Checkpoint strategy choices.** You can save one coarse agent-run checkpoint
  or finer model/tool-call checkpoints.
- **Live stream events.** With `runner_call`, streamed OpenAI output can be
  published as execution events while the flow is still running.
- **Human approval bridge.** Interrupted OpenAI approval runs can be routed
  through `kitaru.wait(...)` and resumed with an explicit approve/reject
  decision.
- **Plain OpenAI code.** Your agent remains an `agents.Agent`; you do not need to
  rewrite it as a Kitaru-specific object.

Supported OpenAI SDK pieces in this first version:

- agent instructions, model settings, output schemas, and normal final outputs;
- local `@function_tool` tools, including per-tool checkpointing in `calls`
  mode;
- agent handoffs, with nested OpenAI agents prepared recursively;
- `RunConfig`, supplied through `run_config_factory=` so each run gets a fresh
  config object;
- approval interruptions via `wait_for_approval(...)` and
  `build_resume_request(...)`;
- MCP servers and hosted tools as OpenAI SDK features when your agent uses them,
  but not yet as their own fine-grained Kitaru checkpoints.

What it does **not** do yet:

- It does not make every OpenAI Agents SDK feature replayable at token-level
  granularity.
- It does not support streamed per-call checkpoints with the `calls` strategy.
- It does not create separate granular checkpoints for hosted tools or MCP calls;
  use `runner_call` for whole-run durability, or local `@function_tool`s when
  per-tool checkpointing matters.
- It does not make partial token chunks durable replay data; replays use the
  final checkpoint result.

## Run modes

You choose how much of the agent run becomes a Kitaru checkpoint with
`checkpoint_strategy=`.

### Runner checkpoint

```python
runner = KitaruRunner(agent, checkpoint_strategy="runner_call")
```

Kitaru places one checkpoint around the outer OpenAI `Runner.run(...)` call.
This gives the flow one clear terminal artifact, so `flow.run(...).wait()` can
return the agent result directly.

Use this when:

- you want the simplest mental model;
- you want `.wait()` to return the final agent output cleanly;
- you want live OpenAI stream events;
- re-running the whole agent turn on replay is acceptable.

Concrete failure story: your flow asks the agent to write a report, then a later
checkpoint fails while uploading the report. With `runner_call`, replay can reuse
the completed agent-run checkpoint and continue after it. If the agent itself
failed halfway through, replay re-runs the whole agent call.

### Call checkpoints

```python
runner = KitaruRunner(agent, checkpoint_strategy="calls")
```

This is the default. Kitaru catches supported model and tool calls as separate
peer checkpoints under the flow.

Use this when:

- the agent has expensive or flaky tool calls;
- you want finer replay units;
- it is okay to inspect per-call artifacts instead of receiving one clean
  `.wait()` value.

Concrete failure story: your agent calls a search tool five times and the fifth
call fails. With `calls`, the first four completed calls can have their own
checkpoint boundaries. That can make debugging and replay cheaper than repeating
the whole turn.

The trade-off is that there is no single terminal artifact for the flow to
return. `flow.run(...).wait()` can raise `KitaruAmbiguousFlowResultError` because
it sees sibling model/tool checkpoints and cannot guess which one is "the" final
result. The artifacts are still visible in the Kitaru UI and retrievable through
`KitaruClient`.

<Callout type="warn">
  Do not wrap `runner.run_sync(...)` with `checkpoint_strategy="calls"` inside
  your own `@checkpoint`. The adapter needs room to open inner model/tool
  checkpoints, so it must run at flow scope.
</Callout>

## Streaming

Streaming is for demos and real workloads where the answer is useful before the
flow finishes. The OpenAI agent writes; Kitaru publishes live execution events;
a terminal watcher or UI can show those events as they arrive.

```python
@flow(cache=False)
def research(prompt: str) -> str:
    result = runner.run_stream_sync(OpenAIRunRequest.start(prompt))
    return str(result.final_output)
```

`run_stream(...)` and `run_stream_sync(...)` return the same kind of final
`OpenAIRunResult` as non-streaming runs. The difference is what observers can see
during execution.

Current streaming rules:

- Streaming supports `checkpoint_strategy="runner_call"` only.
- Streaming must run inside a Kitaru `@flow`, because events need an active
  execution stream.
- Publication is best effort. If live event publishing is unavailable, the
  OpenAI call can still finish and return a final result.
- Cached results skip the live model call, so examples that showcase streaming
  should usually use `@flow(cache=False)`.

To consume raw events from a Python process:

```python
import kitaru

client = kitaru.KitaruClient()
for event in client.executions.events(
    "<execution-id>",
    kinds=["openai_agents.stream.event"],
):
    print(event.payload.get("text_delta", ""), end="", flush=True)
```

For the general checkpoint-progress API that powers these live events, see
[Stream Checkpoint Progress](/guides/checkpoint-streaming).

## Tools

OpenAI Agents SDK tools stay OpenAI tools. Define them as usual, then pass them
to your `Agent`.

```python
from agents import Agent, function_tool

@function_tool
def lookup_order(order_id: str) -> str:
    return f"Order {order_id} is delayed by weather."

agent = Agent(
    name="support_agent",
    instructions="Look up the order before answering.",
    model="gpt-5-nano",
    tools=[lookup_order],
)
```

With `checkpoint_strategy="runner_call"`, the full agent turn is one Kitaru
checkpoint. With `checkpoint_strategy="calls"`, supported model/tool calls can
be represented as separate adapter-created checkpoints.

Tool bodies should still follow normal durability rules: avoid irreversible side
effects unless you are comfortable with what happens on retry or replay. For
example, reading an order status is safe. Charging a card, sending an email, or
posting a Slack message needs an idempotency key or an explicit human gate.

### Handoffs

If your agent uses OpenAI Agents SDK handoffs, keep defining them in the OpenAI
SDK style. In `calls` mode, Kitaru prepares nested OpenAI agents too, so their
model and local function-tool calls can receive the same adapter treatment.

Use handoffs when the agent really changes specialist — for example, a planner
hands off to a writer. Do not use handoffs just to split ordinary Python
workflow steps; Kitaru checkpoints are usually clearer for that.

### MCP and hosted tools

MCP servers and hosted tools can still be part of the OpenAI agent run. The
important distinction is checkpoint shape: today Kitaru's fine-grained tool
checkpointing is for local OpenAI `FunctionTool`s. MCP and hosted tool activity
should be treated as part of the surrounding agent/model run rather than as
separate Kitaru tool checkpoints.

If a tool action must be individually replayable, prefer a local
`@function_tool` and put the external call inside it. If whole-run durability is
enough, keep the MCP or hosted tool in the OpenAI agent and use
`checkpoint_strategy="runner_call"`.

## Approvals

Some OpenAI Agents SDK runs pause for approval. Kitaru represents that as an
interrupted `OpenAIRunResult` with pending state. You can either build a resume
request directly, or ask Kitaru to wait for a human decision inside the flow.

```python
from kitaru import flow
from kitaru.adapters.openai_agents import OpenAIRunRequest, wait_for_approval

@flow
def guarded_run(prompt: str) -> str:
    result = runner.run_sync(OpenAIRunRequest.start(prompt))
    if result.status == "interrupted":
        resume = wait_for_approval(result, name="Approve OpenAI tool call")
        result = runner.run_sync(resume)
    return str(result.final_output)
```

Use this for tool calls where the agent needs permission before doing something
externally visible. The wait belongs in the flow body, not inside a checkpoint,
for the same reason `kitaru.wait(...)` belongs at flow scope elsewhere in
Kitaru.

## Gotchas

### The agent must run in flow scope

Call `runner.run_sync(...)`, `runner.run_stream_sync(...)`, or their async
versions from inside a Kitaru `@flow` body. That gives Kitaru an active execution
where checkpoints and live events can be attached.

### `.wait()` is easiest with `runner_call`

If you want:

```python
answer = flow.run(...).wait()
```

to return one clean Python value, prefer `checkpoint_strategy="runner_call"`.
Use `calls` when per-call replay is more important than a single flow return
value.

### Streaming is not transcript durability

Live token chunks are like radio chatter during the run. They are useful to
watch, but they are not the replay source of truth yet. The durable value is the
completed checkpoint result.

### Cached demos look silent

If you run a streaming demo once and then immediately run it again with caching,
Kitaru may reuse the completed result. That is good for durability, but bad for
a screen recording. Use `@flow(cache=False)` for demos where the point is to
watch fresh live events.

## Example

Run the compact OpenAI Agents adapter example:

```bash
uv sync --extra local --extra openai-agents
uv run kitaru init
export OPENAI_API_KEY='sk-...'

uv run examples/integrations/openai_agents_agent/openai_agents_adapter.py
```

To run the same example with live stream events:

```bash
OPENAI_AGENTS_STREAM=1 \
uv run examples/integrations/openai_agents_agent/openai_agents_adapter.py
```

Optional model override:

```bash
export OPENAI_AGENTS_MODEL='<another-openai-model>'
```

## Research bot

For a larger example, run the OpenAI research bot:

```bash
cd examples/end_to_end/openai_research_bot
uv sync --extra local --extra openai-agents
uv run kitaru init
export OPENAI_API_KEY='sk-...'
uv run python research_bot.py "AI agent durability" --max-searches 2
```

The workflow keeps the original research-bot shape:

```text
planner → submitted search fan-out → writer report
```

The planner and writer run at flow scope through `KitaruRunner` with
`checkpoint_strategy="runner_call"`. The planned searches fan out with
`run_search_item.submit(...)`, so each search is its own durable checkpoint.
Ordinary Kitaru checkpoints publish stable dashboard artifacts such as the
normalized research plan, search summaries, and final report.

The example also uses a local OpenAI Agents SDK `@function_tool` named
`search_web` instead of the hosted `WebSearchTool`. The local tool calls the
OpenAI Responses API with `web_search`, which makes the checkpoint trace clearer
with the adapter's current public behavior.

Look for these artifacts in the Kitaru UI:

- `research_plan`
- `search_summaries`
- `durability_drill`
- `final_report`
- `research_report_metadata`

To test the durable-retry story directly, set
`KITARU_RESEARCH_BOT_FAIL_AFTER_SEARCHES=1` before running the example. It will
fail after the submitted searches complete. Unset the flag and run
`kitaru executions replay <EXECUTION_ID> --from durability_drill_gate`; the
replay should reuse the completed planner/search checkpoints and continue into
the writer. `retry` tries to restart the same failed execution and may be
unavailable on server-backed stacks after a run has concluded.

See also: [Replay and overrides](/guides/replay-and-overrides).
