---
title: Deployments
description: Versioned, immutable snapshots of a flow that consumers invoke through a stable URL.
---

A **deployment** is an immutable, versioned snapshot of a flow. Each call to
`flow.deploy()` (or `kitaru deploy`) builds an image, captures the flow&rsquo;s
entrypoint, schema, dependencies, and stack configuration, and registers the
next version of the flow.

Consumers invoke the flow through one **stable URL**. The Kitaru server resolves
the requested tag or version server-side, starts the selected snapshot on the
configured stack, and returns a `FlowHandle`.

## Mental model

<DeploymentsDiagram />

- Versions are numeric and monotonic (`v1`, `v2`, `v3`&hellip;).
- Versions are kept forever and all remain invocable.
- The flow&rsquo;s invocation URL never changes.
- Tag movements rewrite routing instantly &mdash; no redeploy, no image rebuild.

## Deploying

```python
from kitaru import flow

@flow
def coding_agent(task: str) -> str:
    ...

# Build image, capture snapshot, register next version
deployment = coding_agent.deploy()
```

Or from the CLI:

```bash
kitaru deploy
```

Each deploy produces a new version. Nothing overwrites an earlier one.

## Tags

Tags route traffic to a version without redeploying.

| Tag kind | Example | Behavior |
|---|---|---|
| Reserved | `default` | Exactly one version holds it at a time |
| Exclusive (user-defined) | `prod`, `staging` | One version at a time, like `default` |
| Non-exclusive (user-defined) | `canary`, `rc` | Any number of versions can hold it |

Moving a tag is immediate:

```bash
kitaru flow tag coding-agent --version 3 default
```

```text
Before rollback          After rollback
  default → v4              default → v3
```

The flow URL is unchanged. `POST /invoke/coding-agent` now routes to v3.

## Invoking a deployment

Callers invoke a flow through one stable endpoint. The shape is the same whether
the caller is a human, a service, or an upstream agent.

```bash
# Resolves to the `default` tag
kitaru invoke coding-agent --input '{"task": "fix this bug"}'

# Pin to an explicit version
kitaru invoke coding-agent --version 2 --input @repro.json

# Pin to a named tag
kitaru invoke coding-agent --tag canary --input @payload.json
```

From Python:

```python
handle = coding_agent.invoke({"task": "fix this bug"})
result = handle.result()

# Pin to a version or tag explicitly
handle = coding_agent.deployment(version=2).invoke({"task": ...})
handle = coding_agent.deployment(tag="canary").invoke({"task": ...})
```

Auth is workspace-scoped. A workspace API key or service account can invoke any
flow the caller is authorized for &mdash; there are no per-deployment tokens.

## Schema comes from the snapshot

Every deployment captures the flow&rsquo;s input/output schema. Consumers can
invoke a deployed flow **without source access**: the trigger form, the schema
validation, and the SDK typings all derive from the snapshot, not from live
code.

This lets application teams ship new versions independently of consumers, as
long as the schema stays backward-compatible. Breaking changes land on a new
version that consumers opt into by pinning.

## Invocation modes

Kitaru&rsquo;s durable runtime is independent of how a flow is invoked.

<InvocationModesDiagram />

| Mode | How it works | When it fits |
|---|---|---|
| **Serverless** | Invocation resolves a flow/version/tag, schedules or cold-starts a runner on the configured stack, returns a `FlowHandle` | Long-horizon agents, batch tasks, anything tolerant of a cold start |
| **Served** | A long-lived API wrapper around a specific flow version keeps a hot runtime, optimized for lower-latency or streaming | Synchronous agent calls, streaming responses, high-QPS endpoints |

The durable execution model is the same in both modes: the selected snapshot
&rarr; runner &rarr; checkpoints &rarr; artifacts and state. Served mode is a latency
optimization on top of the same runtime.

## Debugging across versions

Every run records the **resolved flow version** in its metadata. When a
consumer reports a run id, you jump straight to the version that handled it
&mdash; no guessing which deploy was live at that time.

The flow detail page in the Kitaru UI is version-aware:

- One page per flow (stable URL, same as the invocation URL).
- A version dropdown switches the selected version in place.
- Trigger panel, executions list, logs, and integration snippets all scope to
  the selected version.

## Rollback is tag movement

Because traffic is routed by tag, rollback is not a deploy. It&rsquo;s a tag move.

```text
default → v4          # current production
default → v3          # rollback

POST /invoke/coding-agent
  → now routes to v3, no redeploy required
```

Canary and gradual rollout fall out of the same primitive: put `canary` on `v4`,
invoke with `--tag canary` for internal traffic, then promote by moving
`default` to `v4` and clearing `canary`.

## Fits behind your platform

Kitaru&rsquo;s invocation API is a stable server-side entry point. It does not
have to be the public API your consumers see. Platform teams regularly put an
internal gateway, auth layer, or product-specific API **in front** of Kitaru:

<GatewayStackDiagram />

You keep your auth, entitlements, interceptors, observability, and UI. Kitaru
owns the durable execution layer underneath.
