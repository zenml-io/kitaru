**Stage file:** `stage_2_sandboxed_exec.py`

## The problem

In [Stage 1](/agent-factory/01-durable-agent) the `exec` tool runs shell commands in your host process. The moment an agent can run shell commands, it can also run the wrong one: a bad `rm`, a script that fills the disk, a `curl | bash` it talked itself into.

## What goes wrong without it

If those commands run on the host, the blast radius is your laptop or your production worker. The agent reasons about the filesystem it can see, and the filesystem it can see is yours. A single mistaken command can delete files that have nothing to do with the task.

## What this stage adds

Stage 2 wraps each agent run in a `DockerSandbox` context manager. Every shell command now runs inside a container with its own filesystem and network namespace, so accidental damage is contained to the container and a mounted workspace instead of reaching the host.

## One-time setup

Build the sandbox image once:

```bash
docker build -t agent-factory-sandbox -f docker/sandbox.Dockerfile docker/
```

Or run `bash setup.sh` to build the sandbox + the proxy + mock images at once (used by stages 4+).

## Run it

```bash
DISABLE_CACHE=1 python stage_2_sandboxed_exec.py
```

The flow has two `agent.run_sync()` turns sharing one `with DockerSandbox(...)`. Turn 1 investigates the machine and `cd`s into `/tmp`. Turn 2 writes `summary.txt` "in the current directory", and because the persistent shell carried turn 1's `cd` across the turn boundary, the file lands in `/tmp/summary.txt` without turn 2 ever stating an absolute path.

### Env-var toggles

- `DISABLE_CACHE=1` — force every checkpoint to re-execute (useful when the agent's already cached and you want to see the sandbox actually running shell commands).
- `FORCE_FAILURE=1` — same durability story as Stage 1: turn 1's checkpoint is cached across the failure, so a re-run without the flag serves it instantly.

## What to look for in the logs

```text
[sandbox] Started container e87af8e85ec2 (image=agent-factory-sandbox, /workspace ← workspace_…)
Kitaru: Checkpoint `default` started.
[sandbox] $ cat /etc/os-release
[sandbox]   → exit=0, stdout=285 chars, cwd=/workspace
[sandbox] $ uname -r
[sandbox]   → exit=0, stdout=16 chars, cwd=/workspace
[sandbox] $ whoami
[sandbox]   → exit=0, stdout=4 chars, cwd=/workspace
[sandbox] $ cd /tmp
[sandbox]   → exit=0, stdout=0 chars, cwd=/tmp                       ← cwd changed
Kitaru: Checkpoint `default` finished in 21.0s.
Kitaru: Checkpoint `default_2` started.
[sandbox] $ ls -la && pwd
[sandbox]   → exit=0, stdout=99 chars, cwd=/tmp                       ← still /tmp from turn 1
[sandbox] $ cat > summary.txt <<'EOF' …                              ← writes /tmp/summary.txt
[sandbox]   → exit=0, stdout=237 chars, cwd=/tmp
Kitaru: Checkpoint `default_2` finished in 13.1s.
[sandbox] Stopping container e87af8e85ec2
```

Every `[sandbox]` line is a command running inside the container, never on your host. Notice `cwd=/tmp` carrying from turn 1 into turn 2: that is the long-lived shell described below. You can also watch the container while the flow runs, from another terminal:

```bash
docker ps                                              # see agent_factory_sandbox_<id>
docker exec -it agent_factory_sandbox_<id> bash        # peek inside the live container
```

## How it works

The pieces involved:

- [`agent_factory/sandbox/runtime.py`](https://github.com/zenml-io/kitaru/tree/develop/examples/end_to_end/agent_factory/agent_factory/sandbox/runtime.py) — `DockerSandbox` context manager: `docker run -d` on entry, `docker stop` on exit. Every lifecycle event prints a `[sandbox]` log line and attaches structured metadata via `kitaru.log()` for the dashboard.
- `docker/sandbox.Dockerfile` — minimal `python:3.11-slim` + bash + curl + jq.
- `agent_factory/tools.py` — `build_tools(permission_handler, sandbox=...)` accepts an optional sandbox; the `exec` tool routes through `sandbox.run(command)` when one's provided, otherwise runs in-process.
- A named volume `workspace_<execution_id>` mounts at `/workspace` in the sandbox — durable filesystem state survives flow pause/resume.

**The persistent shell, within a run.** Every `run(command)` call goes through one long-lived `bash --noprofile --norc` process inside the container. Shell state (`cd`, `export`, file descriptors, background jobs) survives across `exec` calls, just like a normal interactive shell. The host writes commands into the shell's stdin and reads back output up to a unique completion-marker line.

## What's simplified for the tutorial

**Shell state is deliberately not preserved across runs.** The bash process dies when the container stops, and we don't try to replay shell state across runs. Bash commands have side effects (`rm`, `git push`, `curl POST`, `psql -c "INSERT…"`) that a `cd + declare -px` snapshot can't capture or undo, so "restoring" a snapshot would silently drop every actual mutation. If the agent needs cross-run durable state, it should write to `/workspace` (a Docker named volume that survives container teardown) or persist specific values via [`kitaru.save()`](/guides/artifacts) and reload them with `kitaru.load()` at the top of the next run.

> **One subtlety on the durability story from Stage 1.** Kitaru caches the agent's *reasoning* (the LLM responses, the tool-call decisions, the turn output as a whole). It does **not** replay the bash side effects of a cached turn. If turn 1 ran `cd /tmp && touch summary.txt` and got cached, a re-run that serves turn 1 from cache won't actually re-execute the `cd` or re-create the file. The next turn that's still live will run against a *fresh* shell. Plan accordingly: side-effecting commands should generally not straddle the same turn boundary as the LLM calls that decided to issue them.

Docker also has limits as a security boundary. The container and the host share one Linux kernel, so Docker contains many accidental filesystem mistakes but is not a hostile-code boundary on its own. The [landing page](/agent-factory) covers that distinction; the upgrade path below is where you would tighten it.

## Production upgrade path

The `exec` tool only depends on a small `run(command) -> ExecResult` shape, so `DockerSandbox` is one implementation you can swap. A fork that needs stronger isolation can put a different backend behind the same interface without changing the agent's tool wiring. Credentials are the next gap: in this stage they still come from the host process, and [Stage 4](/agent-factory/04-credential-proxy) isolates them via a separate proxy container that injects `Authorization` headers based on host patterns.
