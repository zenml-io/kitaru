## The problem

A useful agent task is rarely a single model call. The agent reasons, calls a tool, reads the result, reasons again, and only finishes several turns later. Every turn is a real API call: it costs real money and takes real seconds. And partway through, the process can die for reasons that have nothing to do with your agent: a deploy restarts the worker, the orchestrator reschedules the pod, the machine runs low on memory.

## What goes wrong without it

Walk through a single retry. Turn 1 runs: the model thinks, calls a tool, comes back with a result. That call cost you, say, forty cents and twenty seconds. Then, before turn 2 starts, the worker restarts. A plain agent loop held all of that progress in memory, and memory is gone. So the retry begins again at turn 1: the same model call, the same forty cents, the same twenty seconds, all to rebuild a result you had a moment ago. On a ten-turn task that crashes near the end, you pay for almost the whole run twice.

## What this stage adds

There are really two jobs here. PydanticAI runs the agent loop: it decides what the model does next, calls the tools, feeds the results back in. That is its job, and it does it well. What it does not do, and what no in-memory agent loop does on its own, is survive the process dying. The loop's progress lives in memory, so when the process goes, the progress goes with it.

Kitaru is the other job. It wraps the loop in a durable flow and writes each finished turn to durable storage the moment it completes. Picture the loop as what the agent is thinking right now, and Kitaru as what it has already written down and cannot lose. After a crash, the retry reads back the turns that already finished instead of paying for them again. Running the loop and surviving a crash are two separate jobs; here PydanticAI stays a plain agent loop and Kitaru supplies the durability around it. You get that without learning a graph DSL or rewriting your control flow as a state machine.

This stage's flow has two checkpoints, both real LLM turns. When the process dies between them, the first turn is already written down; the retry loads it from cache and runs only the turn that never finished.

## Run it

The demo uses a `FORCE_FAILURE` env var to simulate a downstream blip between the two turns.

<Steps>

<Step>

Simulate a failure between the two turns. Turn 1 does real LLM + tool work and is checkpointed; the flow body raises before turn 2 starts.

```bash
FORCE_FAILURE=1 python stage_1_basic_agent.py
```

</Step>

<Step>

Re-run without the flag. `default` is served from cache (zero LLM calls), `default_2` runs fresh, the flow returns.

```bash
python stage_1_basic_agent.py
```

</Step>

</Steps>

### Env-var toggles

- `FORCE_FAILURE=1` — simulate the post-turn-1 blip described above.
- `DISABLE_CACHE=1` — force every checkpoint to re-execute even if a prior cached output exists. Useful when iterating on the flow itself.

## What to look for in the logs

Run it twice and watch the two checkpoints. The gap between the columns is the whole point:

| | First run (with `FORCE_FAILURE`) | Second run (no flag) |
|---|---|---|
| `default` | started → finished (multiple LLM calls) | **cached** (instant, $0) |
| `default_2` | (never runs; flow raised first) | started → finished (one LLM call) |
| Outcome | failure | printed output, only second turn re-paid for |

The first run pays for turn 1, then fails. The second run serves turn 1 from cache for nothing and runs only turn 2. The retry rebuilds none of the work that already succeeded.

## How it works

The stage is a small set of pieces, each one a plain Python object:

- `Profile` — a Pydantic model declaring `name`, `system_prompt`, `model`, `allowed_tools`.
- `PermissionHandler` — gates every tool call against the profile.
- `build_tools(permission_handler)` — produces a pydantic-ai toolset filtered by `allowed_tools`.
- `build_agent(profile)` — returns a vanilla pydantic-ai `Agent`.
- The flow body wraps the agent with `KitaruAgent(...)` for durable execution.

The `Profile` is the per-stage gate: stage 1 says `allowed_tools={"exec"}` and `build_tools(...)` filters out everything else. Later stages add tools to the set and gain those capabilities; older stage files stay valid because the library grows monotonically.

## What's simplified for the tutorial

Each stage in this tour explicitly passes `granular_checkpoints=False` to `KitaruAgent` so the stage log blocks read cleanly: one aggregating `default` / `default_2` checkpoint per `agent.run_sync()`, easy to point at while learning. The `FORCE_FAILURE` demo lands at the turn boundary in this mode. This kwarg exists for teaching, not because you would normally set it.

## Production upgrade path

In a real fork you usually remove the teaching-only `granular_checkpoints=False`. `KitaruAgent` defaults to `granular_checkpoints=True`, which means every model request and every tool call gets its own checkpoint and its own cache key. A flow that crashed after the third model request then resumes by replaying only the calls after the third. Same durability story; finer cache granularity, finer dashboard rows.
