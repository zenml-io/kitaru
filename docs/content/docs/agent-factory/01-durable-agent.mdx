**Stage file:** `stage_1_basic_agent.py`

PydanticAI gives you the agent loop. Kitaru gives you durable execution. Together: durable agents without learning a graph DSL or rewriting your control flow as a state machine.

## What's in it

- `Profile` — a Pydantic model declaring `name`, `system_prompt`, `model`, `allowed_tools`.
- `PermissionHandler` — gates every tool call against the profile.
- `build_tools(permission_handler)` — produces a pydantic-ai toolset filtered by `allowed_tools`.
- `build_agent(profile)` — returns a vanilla pydantic-ai `Agent`.
- The flow body wraps the agent with `KitaruAgent(...)` for durable execution.

## The hero demo

The flow has **two checkpoints**, both real LLM turns. A `FORCE_FAILURE` env var raises a simulated downstream blip between them.

<Steps>

<Step>

Simulate a failure between the two turns. Turn 1 does real LLM + tool work and is checkpointed; the flow body raises before turn 2 starts.

```bash
FORCE_FAILURE=1 python stage_1_basic_agent.py
```

</Step>

<Step>

Re-run without the flag. `default` is served from cache (zero LLM calls), `default_2` runs fresh, the flow returns.

```bash
python stage_1_basic_agent.py
```

</Step>

</Steps>

<DurableAgentReplayDiagram />

What you see in the kitaru log lines:

| | First run (with `FORCE_FAILURE`) | Second run (no flag) |
|---|---|---|
| `default` | started → finished (multiple LLM calls) | **cached** (instant, $0) |
| `default_2` | (never runs — flow raised first) | started → finished (one LLM call) |
| Outcome | failure | printed output, only second turn re-paid for |

Without kitaru, step 1's failure would have wasted the first turn's work and you'd pay for *both* turns on the retry. With kitaru, only the part that didn't complete the first time gets re-paid for. **That's the durability story.**

## How it composes

Each stage in this tour explicitly passes `granular_checkpoints=False` to `KitaruAgent` so the stage log blocks read cleanly: one aggregating `default` / `default_2` checkpoint per `agent.run_sync()`, easy to point at while learning. The FORCE_FAILURE demo above lands at the turn boundary in this mode.

In a real fork, you usually remove this teaching-only kwarg. `KitaruAgent` defaults to `granular_checkpoints=True`, which means every model request and every tool call gets its own checkpoint and its own cache key — a flow that crashed after the third model request resumes by replaying only the calls after the third. Same durability story; finer cache granularity, finer dashboard rows.

The `Profile` is the per-stage gate: stage 1 says `allowed_tools={"exec"}` and `build_tools(...)` filters out everything else. Later stages add tools to the set and gain those capabilities; older stage files stay valid because the library grows monotonically.

## Env-var toggles

- `FORCE_FAILURE=1` — simulate the post-turn-1 blip described above.
- `DISABLE_CACHE=1` — force every checkpoint to re-execute even if a prior cached output exists. Useful when iterating on the flow itself.
