**Stage file:** `stage_6_hitl.py`

## The problem

Some questions only the operator can answer: sign-off on an irreversible action, a subjective preference, an ambiguous next step. The agent reaches that point and genuinely should stop and ask a human, not guess.

## What goes wrong without it

The naive version is calling `input()` in the middle of the run. That ties the whole flow to one live process. If the machine restarts while it waits, the run is gone, and there is no way for the human to answer from a dashboard, a CLI, or a REST call on a server. A human might take minutes or hours to respond, and the process sits there the whole time, losing everything if it dies.

## What this stage adds

Stage 6 introduces `ask_question`, a freeform HITL tool that pauses the flow until a human responds. The agent calls it like any other tool; the kitaru pydantic-ai adapter routes the call through [`kitaru.wait()`](/guides/wait-and-resume). From the agent's perspective, `ask_question("...")` returns a string after a brief pause. From kitaru's perspective, the flow paused durably until input arrived, so a restart in the middle does not lose the run.

    kitaru executions list                                          # find the waiting execution
    kitaru executions input <execution_id> --value '"Verified by ops on call"'

## What to look for in the logs

The agent's skill (`skills/with-hitl/default-agent/SKILL.md`) runs this procedure:

1. Look up `lookup_wiki(topic="durability")`, a host-side typed service from [Stage 5](/agent-factory/05-typed-services).
2. Draft a 1–2 sentence summary from the first snippet.
3. Call `ask_question("What suffix should I add before publishing?")`. **The flow pauses here.**
4. Append the operator's answer to the summary.
5. Publish via `publish_summary`. Returns `{message_id, posted_at}`.

So the agent goes: typed-service lookup → human pause → publish, all in one durable flow. The pause is the line to watch for:

```text
Kitaru: Checkpoint `default` started.
…  (skill list/read, exec_service lookup_wiki)
Kitaru: Waiting on `ask_question:1:abc12345` (type=external_input, timeout=600s, poll=5s)
                                              ↑ flow paused here
…  (operator runs `kitaru executions input … --value '"Verified by ops on call"'`)
Kitaru: HTTP Request: POST …   ← agent resumes with the answer
…  (exec_service publish_summary)
Kitaru: Checkpoint `default` finished in 1m12s.

Published 4f12a87bc394 at 1777892841: Durable execution persists every checkpoint output. Verified by ops on call.
```

Once a stage has completed, the operator surface that makes durability *observable* lives behind the CLI and dashboard. From the same shell that ran the stage:

```bash
kitaru executions list                                  # find the execution_id
kitaru executions get <execution_id>                    # full status: turn outputs, wait history, artifacts
kitaru executions logs <execution_id>                   # streaming runtime logs
kitaru executions replay <execution_id> --from default  # re-run from the agent turn (cached HITL answer reused)
```

`replay --from default` re-executes the agent turn with everything upstream served from cache; if the operator already answered the wait in the original run, the cached answer is reused (the wait `name` is stable across replays; the "Wait-name design is replay-safe" note under How it works explains why). For replay with output overrides that swap a checkpoint's input artifact while preserving downstream caches, see [Replay and Overrides](/guides/replay-and-overrides).

## How it works

The pieces involved:

- `agent_factory/tools.py` — adds the `ask_question` tool factory. Body calls `wait_for_input(question=question, name=...)` from the kitaru pydantic-ai adapter. The wait returns whatever the operator supplies; the tool coerces to `str` for the agent's tool-result contract.
- `agent_factory/profile.py` — `ToolName` already includes `ask_question` (forward-looking). Stage 6 just turns it on in `allowed_tools={...}`.
- [`skills/with-hitl/default-agent/SKILL.md`](https://github.com/zenml-io/kitaru/tree/develop/examples/end_to_end/agent_factory/skills/with-hitl/default-agent/SKILL.md) — stage 6's procedure.

A few mechanics worth knowing:

- **No checkpoint plumbing on the example side.** The `wait_for_input` call inside the tool body is the only HITL-specific code in this stage. The adapter handles the suspend/resume mechanics under the hood; the tool body looks like a normal function call that happens to take a while.
- **Wait paths are flow-scope only, so the wait-bearing tool opts out of granular checkpoints.** `KitaruAgent` defaults to `granular_checkpoints=True`, which wraps every tool call in its own checkpoint. But `kitaru.wait()` (and the adapter's `wait_for_input` shim) refuses to run inside a checkpoint body; it has to live at flow scope. Stage 6 wires this by passing `tool_checkpoint_config_by_name={"ask_question": False}` to `KitaruAgent`, which tells the adapter to skip the granular checkpoint wrapper for that one tool. Other tools (`exec`, `skill`, `exec_service`) stay granular.
- **Wait-name design is replay-safe.** Each wait is identified by a `name` of the form `ask_question:<call_index>:<sha1(question)[:8]>`. The call index makes two same-text questions in one turn distinguishable (the runtime DB enforces a unique constraint on `(run_id, name)`); the question hash makes the name stable across replays as long as the agent emits the same question at the same call index.
- **Schema is `None` (any-JSON), not `str`.** The operator can supply any JSON value (a string, a structured object, etc.). The tool body coerces to `str` for the freeform shape.

## What's simplified for the tutorial

- **The tool calls `wait_for_input(...)` from the body instead of decorating with `@hitl_tool(...)`.** The shipped `@hitl_tool(schema=...)` form persists the `schema` value (a Python `type`) into the wait's metadata, which doesn't round-trip cleanly on the local stack today. Calling `wait_for_input(...)` from inside the tool body has the same external behavior without that snag.
- **Operator input flows downstream verbatim.** Whatever the operator answers becomes the tool's return value, then is appended to the summary, then is POSTed to the webhook. There is no escaping and no re-prompting in the example.

## Production upgrade path

On a server the operator answers through the dashboard, CLI, or REST API rather than the local terminal prompt; the non-interactive run above is already that shape. Before handing operator input to anything that interprets the bytes (an HTML renderer, a shell, SQL), escape it yourself; the example passes it through unescaped.
