**Stage file:** `stage_4_credential_proxy.py`

## The problem

In stages 1–3 the agent's `exec` either runs in your host process or in a container with no credentials. Once you give the agent real services to call, the credentials have to live somewhere. "In the worker container alongside the agent's shell" is the wrong somewhere.

## What goes wrong without it

If `WIKI_TOKEN` sits in the worker's environment, a prompt-injected agent can `cat $WIKI_TOKEN` and exfiltrate it. The worker is exactly the process running model-chosen commands, so it is the last place a real secret should be.

## What this stage adds

Stage 4 splits the secret away from the agent. A separate `proxy` container holds the service credentials and adds the `Authorization` header to outbound requests that match a configured host. The worker can still make the call. It just never holds the upstream token that the call needs to succeed.

<CredentialProxyDiagram />

Here is the whole trip one request makes, one step at a time:

1. The agent runs `curl http://wiki.local/snippets/durability` inside the worker container.
2. The worker has no `WIKI_TOKEN`. Look through its environment and the secret is not there.
3. The request leaves the worker through its `http_proxy` setting, so it goes to the proxy container instead of straight to `wiki.local`.
4. The proxy recognizes the host `wiki.local` from its credential map.
5. The proxy adds an `Authorization: Bearer …` header using the real `wiki-token` it holds.
6. The mock wiki sees a valid token and returns `200` with the snippet.
7. The worker reads the response body. It never saw the token that made the request work.

The worker does carry one credential: a per-run bearer token that lets it talk to its own proxy, sitting in the worker's `http_proxy` environment variable. That token only buys access to the proxy. It is not the `wiki-token`, and on its own it cannot authorize a request to `wiki.local`. The credential that actually authorizes the upstream call lives only in the proxy container.

## One-time setup

`bash setup.sh` builds the sandbox + proxy + mock images and creates the `wiki-token` kitaru secret. Idempotent, so it's safe to re-run.

```bash
bash setup.sh
```

## What to look for in the logs

Three containers come up (mock-services, proxy, sandbox), all on the `agent_factory` Docker network. The agent follows its skill, hits `wiki.local` through the proxy, and the proxy injects the bearer:

```text
[mock-services] Started container … (network aliases=['wiki.local', 'webhook.local'], host=http://localhost:<port>)
[proxy]         Started container … (image=agent-factory-proxy, injecting for hosts=['wiki.local'])
[sandbox]       Started container … (proxy-wired)
Kitaru: Checkpoint `default` started.
[sandbox] $ curl -s http://wiki.local/snippets/durability
[sandbox]   → exit=0, stdout=514 chars, cwd=/tmp                ← JSON came back
…  (writes /tmp/summary.txt with a real fact pulled from the wiki snippet)
Kitaru: Checkpoint `default` finished in 41.8s.
```

The proxy + mock containers print correlated logs (use `docker logs <container>` while the flow is running):

```text
[agent-factory-proxy] credentials loaded for hosts: ['wiki.local']
[agent-factory-proxy] proxy token configured
[agent-factory-proxy] injected headers for wiki.local: ['Authorization']
[mock-services] GET /snippets/durability (host=wiki.local, auth=Bearer w…) → 200
```

The `wiki-token` arrived at the mock, but **the worker never had it**. The credential was resolved on the host *once* at flow start (`kitaru.get_secret("wiki-token")`), handed to the proxy container's `AGENT_FACTORY_CREDENTIALS` env, and the proxy injected it on every outbound request to `wiki.local`. A prompt-injected agent inside the worker can't `echo $WIKI_TOKEN` because there *is* no `WIKI_TOKEN` env there.

## How it works

Those seven steps sit on top of five pieces of infrastructure: mitmproxy, a self-signed CA, Docker network DNS, the per-run bearer that gates the proxy, and `{{ secret-name.key }}` template resolution. **The two pieces worth reading the source for are `DockerProxy.__enter__` and `SandboxProxyRule`**: those are where the architecture lives. Everything else (CA generation, the mitmproxy addon, the `agent_factory` Docker network setup) is plumbing you can leave alone unless you're swapping mitmproxy for something else.

The pieces involved:

- [`agent_factory/sandbox/proxy.py`](https://github.com/zenml-io/kitaru/tree/develop/examples/end_to_end/agent_factory/agent_factory/sandbox/proxy.py) — `DockerProxy` context manager. Per-run bearer token wired into the worker's `http_proxy` URL via basic-auth-as-bearer; the addon's auth gate rejects requests without the right token so other host processes can't accidentally use this proxy.
- [`agent_factory/sandbox/proxy_addon.py`](https://github.com/zenml-io/kitaru/tree/develop/examples/end_to_end/agent_factory/agent_factory/sandbox/proxy_addon.py) — mitmproxy addon. Per-connection auth gate + per-request host-match header injection.
- [`agent_factory/sandbox/certs.py`](https://github.com/zenml-io/kitaru/tree/develop/examples/end_to_end/agent_factory/agent_factory/sandbox/certs.py) — self-signed CA generation. Worker trusts the public cert via `update-ca-certificates`; the combined key+cert lives only in the proxy container.
- `agent_factory/sandbox/runtime.py` — `DockerSandbox(proxy=…)` parameter wires `http_proxy`/`https_proxy` env vars + `REQUESTS_CA_BUNDLE` etc. + bind-mounts the public cert + runs `update-ca-certificates` on container start.
- `agent_factory/profile.py` — `SandboxProxyRule(name, hosts, headers)`. Header values can contain `{{ secret-name.key }}` templates resolved via `kitaru.get_secret(...)`.
- `agent_factory/secrets.py` — `build_credential_map(profile)` resolves all templates once on the host before any container sees them.

A few mechanics worth knowing:

- **Templates resolve on the host, before the proxy container starts.** The credential template `{{ wiki-token.value }}` is resolved at flow start and passed to the proxy via Docker env. The worker never sees the resolved value, the template, or the secret name.
- **HTTPS works because the worker trusts the proxy's CA.** The proxy listens for HTTP/HTTPS via `mitmdump --listen-host 0.0.0.0 --listen-port 8080` and intercepts both.
- **DNS via Docker's embedded resolver.** `--network-alias wiki.local` on the mock-services container makes `wiki.local` resolve to that container, so the agent's `curl http://wiki.local/...` lands at the mock without `/etc/hosts` hacks.

## What's simplified for the tutorial

The point of this stage is the trust boundary: the credential that authorizes a call lives on one side, and the process running model-chosen commands lives on the other. Docker, mitmproxy, and the mock wiki are just the cheapest way to draw that boundary on a laptop, and none of them is the lesson. For simplicity the sandbox, proxy, and mock all share one Docker network, so treat the layout as *shape* and tighten it for your environment. Two caveats matter most:

- **Network reachability is not the same as authentication.** Because the three containers share the `agent_factory` Docker network, a process inside the worker could `curl http://wiki.local/...` directly, without going through the proxy. That request fails with `401 unauthorized`, because the mock checks for the `Authorization` header and only the proxy can add it. The secret still holds, but the network path itself is not blocked.
- **The per-run proxy bearer is visible to the worker.** The worker has to authenticate to its own proxy, so the per-run token sits in the worker's `http_proxy` environment variable as basic-auth-as-bearer. A prompt-injected agent could read `$http_proxy` and use the proxy directly. The real credentials still hold: the proxy bearer only gets requests *through the proxy*, and the credentials that matter (`wiki-token` and the like) still live only on the proxy side, so the worker never sees the raw token. What the bearer does *not* do on its own is limit which requests the worker may make. Any call the worker sends to an allowed host gets the injected `Authorization` header, whatever the path or method, so this pattern stops raw-token exfiltration but is not by itself per-path or per-method authorization. The production upgrade path below is where you narrow that.

## Production upgrade path

A real fork hardens that trust boundary on both the network and the secret-handling side:

- use per-role networks: the worker isolated (optionally with egress policies), mock-services reachable only from the proxy;
- constrain the proxy with host, path, and method allowlists, or per-agent proxy rules, so reaching the proxy does not let the worker make arbitrary authenticated calls to an allowed host;
- mount credentials as files instead of env vars;
- prefer mTLS over the per-run basic-auth-as-bearer;
- put the persistent-shell completion signal on a side channel rather than mixing it with stdout.
