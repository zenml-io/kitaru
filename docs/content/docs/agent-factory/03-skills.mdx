**Stage file:** `stage_3_skills.py`

## The problem

In stages 1–2 the agent's behavior is hardcoded in the system prompt. Real agents have playbooks: the specific steps to take, what to check, how to summarize, when to stop. Those steps change often, and the people who want to change them are not always the people who own the Python.

## What goes wrong without it

If the procedure lives in a prompt string inside the agent code, every wording change is a code change. An operator who wants to adjust the triage steps has to open the Python, edit a string, and wait for a deploy. The procedure is also hard to read and review when it is buried in source.

## What this stage adds

Stage 3 introduces the `skill` tool. The agent reads its instructions from `skills/<agent>/SKILL.md` instead of from Python. The system prompt only says "find your skill and follow it." The actual procedure (which commands to run, what to summarize, how to return) lives in `skills/basic/default-agent/SKILL.md`. Edit the markdown, re-run, and the agent's behavior changes without touching Python.

## One-time setup

Stage 3 runs shell commands in the Docker sandbox from [Stage 2](/agent-factory/02-sandbox). If you skipped that stage, build the image once:

```bash
docker build -t agent-factory-sandbox -f docker/sandbox.Dockerfile docker/
```

Or run `bash setup.sh` to build everything at once.

## Run it

```bash
DISABLE_CACHE=1 python stage_3_skills.py
```

<Callout type="info">
  When iterating on a `SKILL.md`, run with `DISABLE_CACHE=1`, otherwise the prior run's turn output is cached and your edits won't visibly change anything until the cache is invalidated.
</Callout>

### Env-var toggles

- `DISABLE_CACHE=1` — same as Stage 2; recommended when iterating on the SKILL.

`skill` is a host-side Python function, not an HTTP call. The `Kitaru: HTTP Request: POST ...` lines you see are the LLM turns that *decide* to call it.

## How it works

The pieces involved:

- `agent_factory/tools.py` — `skill` tool factory with `list` / `read` / `search` actions, `.is_relative_to(skills_root)` escape prevention, `MAX_READ_BYTES=100_000`, default glob `**/SKILL.md`.
- `agent_factory/profile.py` — `LocalSkillSource(path=...)` Pydantic model + `SkillSource` alias.
- `skills/basic/default-agent/SKILL.md` — the agent's playbook for stage 3 (basic procedure with no external services). Operator edits this in their IDE.

The skill tool runs **host-side**, not inside the sandbox. The agent calls the tool from inside its turn checkpoint; the tool reads files from the host's filesystem directly. So operators can edit `skills/...` without touching containers, and the path validation is a single boundary on the host.

## What's simplified for the tutorial

Stage 3 ships one `SkillSource` variant (`LocalSkillSource(path=...)`) for local development. It does not include skill versioning, a review UI, or diff/provenance tracking. The point of this stage is to show where operator-editable procedures plug in, not to ship a full skill-management product.

## Production upgrade path

Forks commonly want one of:

- **`GitRepoSkillSource(repo_url=..., ref=...)`** — clone a versioned skill repo at flow start. The shared-team path: skills are code-reviewed via PRs, shared across teammates and running agents.
- **`InlineMarkdownSkillSource(name=..., markdown=...)`** — bake the markdown directly into the Profile. Useful for one-off agents, tests, or skills generated by another flow.
- **Object storage / kitaru artifacts / container-image bake** — for stricter deployment shapes.

The `SkillSource` seam is visible in `agent_factory/profile.py` so forking devs see the alternatives where the architecture lives, not just in docs. Adding a new source = subclass with a `resolve(self) -> Path` method; the skill tool itself doesn't change. This is also the natural place a production fork would add review, provenance, or version pinning.
