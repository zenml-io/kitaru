# Implementation notes

Decisions taken during the implementation of `design/design.md` that the
design doc did not specify, plus issues that came up and how they were
resolved. Ordered roughly by implementation phase.

## Orchestration

- Implementation order: tags and agents/agent-versions first (parallel),
  then sessions/session-nodes, then cohorts, then replay-configs/replays,
  then experiments/experiment-runs, then the runner and the e2e user code.
- Each vertical initially shipped its own Alembic revision to keep its
  postgres tests runnable. At the end they were squashed into the single
  `004_add_record_replay` revision (autogenerated fresh against the 003
  head, round-trip and empty follow-up autogenerate verified) per the
  one-migration-per-PR rule.

## Decisions

### Tags

- `tag_link.resource_type` is stored as `varchar(64)`, not a Postgres ENUM
  type. The `StrEnum` in the domain and API layers enforces the value set
  and adding a resource type stays a code change.
- The `TagResourceType` enum exists twice (domain and `api_models`) with
  conversion in the REST mapping, since the domain layer imports nothing
  from other layers.
- Attach returns a `TagLinkResponse` with 201. Detach via a nonexistent
  tag id returns 404 `TagLinkNotFound` rather than `TagNotFound`.
- Link creation does not validate that the referenced resource exists.
  The polymorphic reference has no FK and most target tables did not
  exist when tags landed.
- No `owner_id` index on `tag`, matching the design doc which specifies
  one for `secret` but not for `tag`.

### Agents and agent versions

- The frozen value objects (`RunSpec`, `AgentCapabilities`) reuse the
  existing `FrozenModel` from `server/base.py` instead of adding a new
  base in the domain layer.
- Named FK constraints via a new `foreign_key_name()` helper in
  `schema_utils.py` let repositories translate FK violations by name:
  agent delete with versions raises `AgentInUse` (409), secret delete
  while referenced by a run spec raises `SecretInUse` (409), version
  create with an unknown agent raises `AgentNotFound`.
- `AgentVersion.version` uses the shared `Name` type, so dots are
  rejected. Semver labels like "1.0.0" are currently not accepted.
- `RunSpec.timeout_seconds` is `PositiveInt` (design says plain int).
- Duplicate `secret_ids` in a run spec are rejected with a 422 domain
  validation error instead of surfacing the join-table constraint as 500.
- Secret existence is checked in the service and internal secrets are
  treated as not found, matching the internal-secret visibility rule.
- `GET /v1/agents/{id}/versions` returns 404 for an unknown agent
  instead of an empty page.
- PATCH follows the secret convention: `None` means unchanged, so a
  PATCH cannot clear `run_spec` or `description` back to null.
- The design rule that `run_spec` and `capabilities` freeze once a
  replay references the version is deferred to the replay phase.

### Sessions and session nodes

- The canonical-JSON and tool cache-key helper lives in a new top-level
  `kitaru/hashing.py`, importable by both client and server without
  touching the import-linter layer contracts. The runner uses the same
  `tool_call_cache_key` client-side.
- Node key occurrence suffix: the first occurrence is unsuffixed and
  `#2` starts at the second occurrence. The design doc example
  (`tool_call:get_weather#1`) suggests suffixing the first occurrence,
  the unsuffixed form was chosen deliberately.
- Recorded sessions must be created `in_progress`, and `provider` is
  rejected on non-imported sessions. `origin=replay` creation is
  rejected until the replay phase adds the `replay_id` link. The field
  is absent from the create DTO rather than accepted and ignored.
- `agent_version_id` on create is validated to exist and to belong to
  the session's agent.
- Node payload exclusion: one `SessionNodeResponse` whose `inputs`,
  `outputs`, and `attributes` are null unless `include_payloads=true`.
  The repository defers those columns so list queries never select
  them. Node endpoints return plain sequence-ordered lists, not pages,
  and batch upsert returns 200.
- A node id reused across sessions is a 409 instead of silently
  mutating the other session's node. Secondary parent ids follow the
  same parent-before-child rule.
- Token range filters treat sessions without usage as total 0, cost
  filters exclude NULL-cost sessions (SQL NULL semantics). Rollup token
  fields stay `None` per field when no node reports that field.
- `cache_key` computes for every `tool_call`, hashing an absent tool
  name as `null`.

### Cohorts

- Creation from a `filter` rejects an explicit `agent_id` in the request,
  the agent comes solely from the filter, which must pin one. With
  explicit `session_ids`, `agent_id` is required and explicit id order
  defines member positions.
- Duplicate ids inside `session_ids` are rejected rather than
  deduplicated.
- `filter_snapshot` stores the application filter as JSON without
  pagination fields.
- Filter resolution iterates repository pages of 1000 internally.
- Session delete is blocked with 409 while the session is in a cohort,
  via named-FK translation. The tag-link cleanup and row delete now run
  inside one savepoint so a blocked delete does not leak the tag-link
  deletion.
- The shared `?tag=` filtering subquery moved into
  `adapters/db/tag_filtering.py`, used by session and cohort list
  queries.

### Experiments, experiment runs, and replays

- `replay.attempt` starts at 1, requeue increments it.
- Run `number` allocation serializes via `SELECT ... FOR UPDATE` on the
  experiment row inside the run repository create.
- Design 3.10 lists both a unique constraint and an index on
  `(experiment_id, number)`. Only the unique constraint was created,
  since the DB rules forbid a redundant index on the same columns.
- "Latest runnable" resolves by descending UUIDv7 id (creation order).
- The scorer source wire format is the string `module:attribute`
  (pattern-validated), converted to the structured domain `SourceRef`
  in mapping.
- Experiment tool policy defaults to passthrough when omitted,
  standalone replay tool policy defaults to
  history(original_session, on_miss=fail), per design section 5.
- Config PATCH follows the repo `None`-means-unchanged convention, so an
  override cannot be cleared back to null. Unchanged bundle parts carry
  over from the old config row into the new one, and the old row is
  garbage-collected when unreferenced (delete in a savepoint, swallow
  the RESTRICT violations).
- Experiment and replay responses expose no `replay_config_id`, only the
  inlined config contents.
- Explicit version without a run spec is 409, no runnable default is
  409, cross-agent version is 422, original session in progress is 422.
- `SessionInUse` and `AgentVersionInUse` carry a referrer so messages
  distinguish cohorts/replays/sessions as the blocking reference.

### Replay execution workflow

- Session linking: `replay_id` requires request `origin=recorded` and the
  server rewrites it to `replay`. Explicit `origin=replay` without a
  `replay_id` is rejected.
- An empty claim finalizes a drained run. A stale requeue can time out
  the last replay with no PATCH ever following, so without this a run
  whose worker died at max attempts would poll forever.
- Reads report stale claims exactly as the next claim would write them
  (pending with attempt+1, or timed out), without writing.
- The input diff reports the system prompt with `original: null` since
  the original system prompt is never recorded.
- Run summary shape: `replay_counts_by_status`, `pass_rate` (fraction
  among scored replays, null when none), `scores.{name}.{baseline,
  replay}.{mean,median}`, `total_cost.{baseline,replay}`, all floats.
- Tool lookup: non-history policy for the tool and cache-key mismatch
  are 422. Most recent means `started_at` desc nulls last, then id
  desc. Mocked exclusion treats boolean true or string "true".
- Completed PATCH requires the full scoring result, failed/timed_out
  require an error. Heartbeat on a canceled replay answers
  `{canceled: true}` without writing, any other non-active status is a
  409 so a zombie of a requeued attempt stops instead of resurrecting
  the replay.
- The design's run-level `failed` for a spec that no longer resolves at
  claim time is not implemented. The claim does not resolve specs, a
  deleted secret surfaces as 404 on the spec fetch instead.
- Known gap: a canceling run with a stale running replay never drains,
  since claim returns early for canceling runs and the dead worker
  sends no heartbeat. Cancel would need to also reap stale running
  replays.

### Runner and scoring

- The scoring contract lives in top-level `kitaru/scoring.py`:
  `SessionView` (session + nodes wire models), `load_scorer`,
  `run_scorer`, `evaluate_scoring_policy`, plus client-side
  `ScoringResult`/`ScoringError` (no wire DTO exists for the result and
  the domain one is off-limits to client code).
- Threshold semantics: `score >= pass_threshold` passes,
  `value <= fail_below` hard-fails, both edges tested.
- Zero total scorer weight raises `ScoringError`, the runner turns it
  into a failed replay.
- `KITARU_INPUTS` is set only when the JSON fits 32768 bytes, a client
  constant. The design wants the threshold server-configured, serving
  it from the spec is deferred.
- Env layering for the agent process: `os.environ` < `run.env` <
  `secret_env` < contract vars. An inherited `KITARU_INPUTS` is popped
  so an over-threshold replay cannot leak a stale value into the child.
- Runner defaults: heartbeat 10s against the 60s server timeout, claim
  batch size defaults to concurrency, 2s run-status poll, 8 KiB log
  tail in error messages.
- Baseline scores are posted via the merging scores endpoint with only
  newly computed values. A baseline scorer error also fails the replay.
- No CLI, the runner is a Python API (`kitaru.Runner`), per the goal.

### E2E user code (`user_code/`)

- `MockAgent` simulates llm and tool calls deterministically: every llm
  output, token count, and cost is a hash of (model, model_params,
  messages, step index), and messages embed the system prompt, inputs,
  and prior tool results, so overrides and mocked tool results visibly
  change outputs, cost, and scores. Default scenario: plan llm call,
  `get_weather`, `calculate`, answer llm call.
- Adapter hooks: run start/end/error, llm call start/end, tool call
  start/end, plus a tool interceptor seam
  `(tool_name, arguments, default_executor) -> result` used for tool
  policies, and `configure(model, system_prompt, model_params)` used
  for replay overrides.
- Node tree: root span "run", llm calls under root, tool calls under
  the most recent completed llm call (falling back to root). The root
  span is flushed in_progress immediately and re-upserted terminal at
  run end.
- Sync-over-async: background event loop thread, same pattern as
  `KitaruSyncClient`.
- A fatal policy miss (`on_miss="fail"`) records the tool node failed
  without mocked attributes, since nothing was mocked.
- The adapter vendors a local UUIDv7 generator (stdlib gains
  `uuid.uuid7` only in 3.14 and `server.domain.ids` is server-only).
- Per an instruction mid-implementation there are no tests for
  `user_code/`. Verification ran as scratchpad smoke scripts covering
  recording, determinism, overrides, all tool policies, and scorers.

### E2E scripts

- `./scripts/run_e2e.sh` is the whole flow: brings up the db container,
  drops and recreates a dedicated `kitaru_e2e` database, starts the
  server on port 8300 (override with `KITARU_E2E_PORT`), waits for
  health, runs `scripts/e2e_test.py`, and always tears the server down,
  propagating the driver's exit code. To run the driver against an
  already-running server:
  `KITARU_E2E_API_URL=http://127.0.0.1:8300 uv run python scripts/e2e_test.py`.
- The driver covers: login as the bootstrap default account and API key
  creation, secret plus agent plus runnable agent version, 4 regular
  agent executions with node-tree and rollup assertions, cohort and
  experiment (model override, history default policy plus per-tool
  static entry, 3 weighted scorers), run with `score_baselines=true`,
  in-process runner execution, run summary and per-replay
  score/diff/mock assertions, baseline writes, a standalone replay, and
  negative controls (frozen experiment config PATCH 409, empty claim on
  a drained run).
- Chicken-and-egg on the version id in the run spec env: the version's
  run_spec is patched with `KITARU_E2E_AGENT_VERSION_ID` after
  creation, legal until a replay references the version.
- The run_spec command uses the absolute venv python
  (`<repo>/.venv/bin/python -m user_code.main`) with the repo root as
  working directory.

## Issues

### SDK discriminated-union serialization bug

- Client resources dump requests with
  `model_dump(mode="json", exclude_unset=True)`. For discriminated
  unions in the wire models a default-constructed member like
  `PassthroughPolicy()` serialized as `{}` because its `type`
  discriminator was never explicitly set, so the server rejected the
  request with 422 `union_tag_not_found`. Found while building the e2e
  user code. The fix is a `ToolPolicyBase` whose `model_post_init` adds
  `type` to `model_fields_set`, so `exclude_unset` keeps the
  discriminator for all four union members. Tool policies are the only
  discriminated union in `api_models`, and the OpenAPI schema is
  unchanged. Side effect: the client test asserting a 422 for a
  cohort-scope standalone replay previously passed for the wrong reason
  (the missing discriminator caused the 422), it now exercises the
  intended server validation.

### Pre-existing repo state

- `just check` typecheck reports 422 pre-existing diagnostics, all in
  `examples/` referencing the deleted v1 API. Identical on the base
  branch, zero diagnostics in `src/` or `tests/`. Rewriting the examples
  against the v2 SDK is out of scope here.
- The `actionlint` and `lychee` binaries are not installed on this
  machine, so those two `just check` recipes cannot run locally.

### Tags

- Alembic autogenerate emitted `sqlmodel.sql.sqltypes.AutoString` without
  the matching import, added by hand (revision 003 needed the same).
- Attaching a link races a concurrent tag delete: the service checks the
  tag exists before insert, but a delete between check and flush surfaces
  the raw FK IntegrityError. Closing it needs named-FK constraint
  translation support in `schema_utils` (added later by the agents
  vertical as `foreign_key_name()`, the tag FK was not retrofitted).

### Sessions and session nodes

- `metadata` is reserved on SQLModel, stored as attribute `metadata_`
  with an explicit `Column("metadata", JSONB)`. `model_params` trips
  pydantic's protected `model_` namespace, silenced with
  `protected_namespaces=()` on the affected models.
- Deferred payload columns on an async session raise `MissingGreenlet`
  when touched after flush, so `to_domain` never reads deferred
  attributes and the upsert assigns every field before reading.
- `has_score` on JSONB compares against `sa.literal({}, JSONB)`.
- `Numeric(12,6)` round-trips as `Decimal("0.750000")`, tests compare
  `Decimal` values.

### Replay execution workflow

- SQLAlchemy savepoint trap: mutating an ORM row before
  `begin_nested()` lets autoflush run outside the savepoint, poisoning
  the transaction on FK violation. Field changes are applied inside the
  savepoint in the replay update. `SQLSessionRepository.update` has the
  same latent pattern, pre-existing and left untouched.
- Staleness-aware progress counting stays a SQL GROUP BY via a CASE
  expression over `coalesce(heartbeat_at, claimed_at)`.
